# Weekly rhythm

**Work sample.** The weekly plan for the pilot, dated April 1, 2026. It splits the work into two lanes and protects the product lane. Names are removed.

---

## Two lanes

**Product:** observations, hypotheses, design decisions, the touchpoint map, and the sprint's deliverables. This is the point of the sprint.

**Project:** daily check-ins, routing work to the scoped instances, Asana, stakeholder communication, leadership briefs, the decision log. Necessary, but timeboxed.

**The rule:** product gets first priority every day, and project work fills the gaps. If project work creeps into product time, the build cycle breaks.

---

## The week

| Day | Product | Project |
|-----|---------|---------|
| **Monday** | Review what the cohort instance built: is it deployed, working, ready for Wednesday's test? Then open time for deliverables. | 15-minute check-in. Afternoon: talking points for Tuesday's leadership check-in, light most weeks. |
| **Tuesday** | Three hours of focused product work before the meeting, four after. | Check-in, the leadership meeting, then an hour to log decisions, route action items and update status. |
| **Wednesday** | Afternoon: prepare an observation lens for the session. Evening: the cohort session, observed with product eyes, then quick bullet notes while it's fresh. | Short check-in. The day is flipped for the evening session. |
| **Thursday** | Protected. Morning: write the full observations and the week's hypotheses. Afternoon: work through them with the UX researcher, then start shaping the build spec. | Check-in only. |
| **Friday** | Morning: finalize the hypothesis, write the build spec, hand it to the cohort instance to build Monday and Tuesday. | Afternoon: Asana, stakeholder follow-ups, a buffer. |

Every other Friday is a sprint review in place of the design block: did the automations create value, is the weekly cycle working, what did we learn? The Monday after is sprint planning, where the riskiest assumption for the new sprint gets named.

---

## The time budget

| Lane | Target | Hours a week |
|------|--------|--------------|
| Product | about 70% | about 28 |
| Project | about 20% | about 8 |
| Buffer | about 10% | about 4 |

---

## Starting a session

Each Claude Code session was meant to start by saying which hat I'm wearing:

- **"Project session":** pull up the instance statuses, Asana, stakeholder context. Check-ins, routing, briefs.
- **"Product session":** pull up the touchpoint map, observations, hypotheses, deliverables. Analysis, design, specs.

It keeps the session in its lane from the first minute.
